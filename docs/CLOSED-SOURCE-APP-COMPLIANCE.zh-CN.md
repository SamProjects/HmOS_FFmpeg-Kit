# 鸿蒙闭源应用使用 FFmpeg HAR 的开发与分发规范

本文可交给后续负责鸿蒙应用开发的 Codex，并在任务中明确要求遵守。适用于应用使用本项目 LGPLv3 配置的 FFmpeg HAR；它是工程实施与验收规范，不是对任何最终应用的法律合规认证。

## 1. 目标与适用范围

- 应用的原创业务代码可以保持闭源；不能把 LGPL 库及其修改作为私有业务代码而拒绝提供相应源码。
- 开发、运行测试与对外分发分别验收。功能测试通过、动态链接或日志显示 LGPL，均不能单独证明分发合规。
- 对外提供 HAP、通过应用市场分发或向客户交付时，落实适用的源码、许可、重链接及安装信息要求。
- 若升级 HAR、改变依赖、修改构建参数或更换签名/分发方式，重新核验受影响项目，不沿用旧版本结论。

## 2. 当前依赖基线与未完成项

当前已发布的候选基线：

| 项目 | 内容 |
|---|---|
| FFmpeg Kit | v1.0.3，extended 全架构命令版 |
| 文件 | `hmos-ffmpeg-1.0.3-extended-all-command-test.har` |
| SHA-256 | `2f81372391557a629ab8e1a074b95d142ab118758cfc7e1217eb31367abee834` |
| FFmpeg | 9.0.2 |
| 架构 | arm64-v8a、x86_64，每架构 10 个动态库 |
| 构建配置 | `--enable-version3 --disable-gpl --disable-nonfree` |
| 链接结构 | ArkTS/NAPI 桥接动态链接独立的 FFmpeg 库和命令库 |
| 功能验证 | 用户反馈 x86_64 DevEco 本地模拟器 97/97 项通过；不等于许可验收 |

正式分发前必须处理以下未完成项：

1. **Codec2 许可版本核验**：当前锁文件写为 `LGPL-2.1-or-later`，但 1.2.0 部分源码头只明确写 LGPL 2.1。核实适用授权和组合条件，记录依据并修正元数据；不能凭本项目白名单检查就视为已解决。若需要调整依赖或构建，生成新版本，不能悄悄替换同一个已发布附件。
2. **完整对应源码交付**：目前有构建脚本、版本锁定和适配补丁，但应用分发方仍需安排清晰、持续可获取且与实际二进制匹配的源码交付方式。
3. **库替换、重链接和安装验证**：目前尚未验证最终鸿蒙闭源应用在其实际签名、安装和分发条件下满足这些要求。

这些问题不能通过增加一段免责声明代替处理。未解决时应明确报告缺项，不宣称“闭源商用分发合规已完成”。

## 3. 依赖与链接要求

1. 固定 HAR 版本、下载来源、SHA-256、包内依赖版本和目标 ABI。保存实际使用包的清单，不以文件名作为唯一身份。
2. 核验实际二进制对应的构建配置及依赖许可证。保持 GPL/nonfree 禁用；不得擅自加入 x264、x265、Xvid、FDK-AAC 等不符合本配方许可边界的组件。
3. 保持应用/原创桥接与 LGPL 组件之间清楚的动态库边界。不得把 FFmpeg 或其他 LGPL 库静态合入私有业务库后，仍直接沿用当前动态链接方案的合规结论。
4. FFmpeg 动态库内部还静态包含部分外部依赖。源码交付和库重建材料必须覆盖实际包含的相关代码，不能只处理外层的几个 `.so`。
5. FFmpeg 命令库包含经过适配的 fftools 代码，属于需要按适用 LGPL 条款提供源码与修改材料的范围。不能因为增加了 NAPI 包装或项目自有代码采用 MIT，就把整个命令库视为可独占闭源。
6. `CONFIG_GPL=0` 等结果只证明配置门禁。还应核对实际链接依赖和许可版本；不得人为修改许可证字符串、检测结果或归档记录来通过检查。

## 4. 许可证与用户可访问的声明

应用应提供易于访问的“开源许可”或同等入口，至少包括：

- 使用了 FFmpeg 及相关开源组件的明确说明。
- 适用的版权声明、LGPLv3 和其引用的 GPLv3 完整文本，以及其他依赖要求的许可、NOTICE、专利等声明。
- 当前应用版本对应的开源组件版本和源码获取地址/方式。
- 哪些开源组件经过修改、如何获取修改内容的说明。

随应用保留依法要求附带的许可文本，不能仅链接一个可能失效的外部页面。检查最终 HAP 和实际安装应用，确认打包过滤、资源压缩或裁剪没有丢弃这些材料。

应用用户协议可以保护原创业务代码，但不得排除适用 LGPL 所授予的权利，特别是不得禁止为调试 LGPL 库修改所必需的逆向工程。不要使用与此冲突的无例外禁止条款。

## 5. 对应源码与构建材料

为每个实际分发版本建立独立、可追溯的源码交付记录，覆盖：

- 与发布二进制准确对应的 FFmpeg 和相关依赖源码。
- FFmpeg 命令组件的完整适配内容、项目加入的相关源文件，以及实际使用的补丁和生成脚本。
- 依赖的实际修改，包括通过宏等方式对内部符号进行隔离的构建设置。
- 配置参数、编译/链接脚本、版本锁定、所需接口文件和工具链要求等必要构建材料。
- 必要的重链接材料；如选择 LGPLv3 §4(d)(0) 路径，提供可供用户重链接的 Corresponding Application Code 及相关条件。它可以是符合要求的目标代码，不必当然公开全部业务源码。

源码获取方式按所选许可条款落实。例如网络分发采用 GPLv3 §6(d) 所述方式时，应在二进制获取位置旁提供清晰的源码获取指引和等价访问；源码可由合适的另一服务器提供，但分发者仍需确保可用且准确对应。

仅提供上游首页、一个模糊的 latest 分支、锁文件或补丁文件，不能自动替代完整对应源码。也不要求所有场景必须把源码压缩包塞进 HAR：可以采用符合条款的独立交付方式。

从实际提供给用户的位置下载材料，验证版本和哈希，并在独立目录按文档重建相关库。记录结果；无法取得或重建时说明原因并补齐材料。按采用的交付条款维持必要的可用期限，不随意删除旧应用版本对应的源码。

## 6. 鸿蒙库替换、重链接与安装

必须为最终应用选择并验证适用的 LGPLv3 §4 路径：

- **§4(d)(1)，合适的共享库机制**：核验用户能使用接口兼容的修改版库，且应用能够正常运行。HAR 内有 `.so`、开发者可以重编译，均不足以单独证明满足此项。
- **§4(d)(0)，重链接材料路径**：提供条款要求的 Minimal Corresponding Source、适合重链接的 Corresponding Application Code 及必要材料和条件，让用户能够形成修改后的组合程序。

按 LGPLv3 §4(e) 和其引用的 GPLv3 §6，评估是否还需要提供 Installation Information；该项有具体适用条件，不能一概忽略，也不能一概声称所有软件都必须公开签名密钥。

在鸿蒙上至少完成以下工程验证：

1. 根据对应源码构建一个带可辨识标记、公共 ABI/SONAME 兼容的修改版库。
2. 按交付给用户的材料替换 HAR 中的相关库或执行重链接，生成修改后的应用包。
3. 使用所声明的用户可行签名、安装流程，在目标设备安装并运行该包。验证账号、签名和安装条件，不能只记录开发者本人的特权环境成功。
4. 通过版本标记或其他可验证行为，确认实际加载了修改版；再执行一次真实媒体处理，确认组合程序仍可运行。
5. 记录签名、应用身份、更新策略、许可证校验、完整性校验等是否阻止了适用条款要求允许的修改和安装。只在模拟器允许未签名包时成功，不能代替商用手机场景验证。

不能默认把公开生产签名私钥作为解决方案。若现有签名或分发机制无法满足适用要求，应提出可验证的替代交付/重链接方案；无法解决时明确列为正式分发阻碍，不以“鸿蒙限制”直接豁免。

已有工程流程参考 [LGPL 库替换/重链接验证](replacement-and-relink.md)。

## 7. 验收记录与分发门禁

后续 Codex 应在应用工程保存一份不含私钥或其他凭据的验收报告，至少记录：

| 验收项 | 必须提供的证据 |
|---|---|
| 实际组件身份 | 应用版本、HAR 来源/版本/哈希、实际动态库清单及哈希 |
| 许可审查 | 依赖许可证及版本依据、实际配置、未解决问题；单独记录 Codec2 核验结果 |
| 声明可访问 | 最终包中的文本清单和安装后用户入口验证 |
| 对应源码 | 对应关系、实际获取位置、下载结果和重建材料/结果 |
| 选定的 §4 路径 | 共享机制或重链接方案及其具体实现和材料 |
| 安装信息适用性 | 判断理由；适用时记录所提供的信息和安装验证 |
| 替换运行 | 原/修改库哈希、设备/API、工具链、签名模型、操作步骤、日志和媒体处理结果 |
| 分发方式 | 测试交付、客户交付或应用市场，以及与验证条件的差异 |
| 未完成事项 | 明确的缺项、影响和解决方案，不能将“待验证”填写为“通过” |

对外正式分发前，不得把仍未解决的必需项标记为通过。应用仍可继续开发和功能测试；报告应准确区分“功能可用”“构建配置通过”和“分发要求已落实”。

软件许可证不等于编码格式的专利授权。按使用的编码器、发行地区和商业模式单独核验相关权利，不将 LGPL/BSD/Apache 配置解释为免除全部专利义务。
