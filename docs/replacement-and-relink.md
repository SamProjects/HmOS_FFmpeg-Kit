# LGPL 库替换/重链接验证

当前 release 仅发布工程预发布版；本仓库没有目标设备和签名安装凭据，未宣称该项已通过。

应用分发者应保存原生桥接、公共 ABI、编译参数、依赖闭包、Hvigor 配置与应用安装流程。用同一 FFmpeg major ABI 构建一个可区分且接口兼容的 LGPL 库，保留本包 SONAME；将消费工程依赖的 HAR 解包到本地源码模块，替换其 libs/arm64-v8a 下对应库，重新用 Hvigor assembleHar，再让应用依赖新 HAR、重建/签名/安装 HAP。在设备上通过 FFmpeg.getBuildInfo 和实际媒体处理确认替换库被运行。

上述步骤是待验证流程，不保证每种应用分发签名模型都允许用户执行。消费者不能仅因 HAR 有 so 就宣称已满足 LGPLv3 §4。若所选共享机制实际不支持兼容修改库，需要设计并审阅可行的重链接交付方式；必要时提供适合重链接的应用目标文件及相关条件，而非擅自公开整个私有源码或擅自省略义务。

记录应用包哈希、原/替换库哈希、ABI、设备/API、工具版本、签名模型、命令、日志和成功/失败结果。不可实现时暂停正式分发；EULA 不应禁止为调试 LGPL 库修改所必需的逆向工程。
